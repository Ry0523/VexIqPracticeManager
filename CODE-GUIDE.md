# Code Guide

This guide maps the hand-maintained source. Do not edit `apps-script/dist-iq/` or `apps-script/dist-v5/`
directly; `build-apps-script.js` generates those bundles from the source modules below.

## Runtime Flow

`index.html` loads the selected game definitions and practice views, then the rule modules, domain models,
storage, and UI controllers. `game.js` selects the active definition. `app.js` coordinates the page and event
state; specialized UI controllers mount into the page and call the domain models. In the browser, modules
publish named globals; under Node.js, the same modules expose CommonJS exports.

Persisted event data is validated by `event.js`. Posted results are captured in `history.js`, which is the
durable analysis/export record. V5 practice field state is stored as opaque `gameData`; the matching game
definition validates and scores it. Shared saves pass through `storage.js` and are merged by `changes.js` on
the Apps Script server.

## Module Contracts

- `EventRules` combines `MatchScoring`, `MatchScheduling`, and `TeamRoster` for existing consumers. New code
  should import the narrow module it owns when practical.
- JSDoc imports reference `types.d.ts`; use those named interfaces instead of bare `object` for shared
  contracts. Keep game-only payloads generic (`unknown` in shared code) and narrow them inside the owning game
  module.
- Game definitions own game-specific score schemas and rules. Optional `practice` capabilities describe
  supported modes, scrimmages, and field APIs; game practice views implement `render`, `read`, `update`, and
  `handleClick`.
- `History.practiceRecord` accepts common run metadata plus optional opaque `gameData`. It delegates custom
  field validation/scoring to the record's game definition; generic history code must not inspect
  game-specific field structure.
- `EventStorage` is the persistence boundary. Local storage uses IndexedDB; the shared app uses Apps Script
  RPC, revision checks, and change-based merges.

## Data Flows

### Match Scoring

1. `game.js` selects `ACTIVE_GAME`; the game's `layout` describes the score-entry groups and counters.
2. `app.js` renders those counters with paths into the game-owned goal object. Each input carries its path,
   point value, and optional limit as data attributes.
3. On input, `updateCalculator` rebuilds the goal object from those paths, then calls `EventRules.goalCounts`
   and `EventRules.score`. The game definition validates and converts its goal shape into aggregate scoring
   counts.
4. `postScore` places the validated counts, goal breakdown, result statuses, and any finals Stop Time into the
   active match result. `saveResultChange` appends a history snapshot before calling `persist`.
5. `EventModel.validate` validates loaded or imported event state. `EventStorage.save` writes locally to
   IndexedDB or sends a shared-app RPC. Shared saves are diffed in `changes.js` and merged and validated by
   `apps-script/Code.gs`.
6. Qualification standings are derived from active match results by `scheduling.js`; `history.js` resolves
   append-only audit records for analysis and export. A correction changes the active result and appends an
   audit revision rather than rewriting the earlier history entry.

### Practice Runs

`practice.js` owns the common team selection, timer, draft, and save lifecycle. For games without a custom
field, it uses the shared score calculator. For a custom field, it passes opaque `gameData` through the game's
practice adapter; shared code does not inspect that structure. The game evaluates the field data, and
`history.js` validates it against the resulting score when creating or loading the practice record.

### Shared Persistence

`storage.js` chooses local IndexedDB or Apps Script RPC. In shared mode it tracks the server revision and base
snapshot; `changes.js` computes item-level changes so independent edits can merge. The server validates access
and data under its lock before committing. A conflict is surfaced to the page instead of overwriting newer
data.

## Adding a Game

1. Add `games/<id>/definition.js`. `game.js` checks for required fields: stable `id`, `name`, `program`,
   `season`, `manual`, `scoring`, `score`, `emptyGoals`, `goalCounts`, `goalsFromCounts`, `layout`,
   `skillsTiebreak`, and `csv`. Keep the ID stable once data is saved under it.
2. Define the game's scoring shape and conversion boundary. `score(counts)` owns point calculation;
   `goalCounts(goals)` validates game-shaped inputs and returns counts in scoring-element order;
   `goalsFromCounts(counts)` rebuilds the game's goal shape. `layout` references those elements for the shared
   calculator.
3. Register the definition in both runtimes: load its script from `index.html` for the browser and add its
   `require` to the definitions list in `game.js` for Node.js.
4. Add its stylesheet and field image, if used, and reference them from source HTML and the definition.
   `build-apps-script.js` inlines the selected game's stylesheet and declared `fieldImage` into the standalone
   bundle.
5. For a custom practice field, add `games/<id>/practice-ui.js` and load it from `index.html`. Export a view
   adapter with `render`, `read`, `update`, and `handleClick`; provide the paired `practice.field` API
   (`empty`, `validate`, `evaluate`, and optional `normalizeForMode`) in the game definition. Add
   game-specific payloads to `types.d.ts` without exposing their internal shape to shared practice/history
   code.
6. Add or extend unit tests for definition validation, scoring limits, goal conversion, and practice
   evaluation. Add browser coverage for custom UI or workflows, then build with `npm run build:iq` or
   `npm run build:v5`. For a separate deployment target, update the build script, package script, clasp
   configuration, and deployment README together.

## Verification

- `npm test` runs the Node.js unit/model suites.
- `npx playwright test --workers=1` runs browser workflows.
- `npm run build:iq` builds the IQ deployment; `npm run build:v5` builds V5.
